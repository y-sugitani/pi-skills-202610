# 知識管理 (Knowledge Management)

vault の**読み書きの手段**と、progress / journals / keywords の**規則**をここに置く（I/O アダプタは無い）。
接続先が決まらないなら **中断**。

## 接続（vault の宣言）

vault の名前・パスはこの skill に書かない。読む側のリポジトリ（またはユーザー）の **AGENTS.md の `## Wiki` 節**を宣言として読む。
宣言が無い・パスが実在しない・複数候補で決まらない → **作業中止**。AGENTS.md への追記を促す（勝手に推測しない）。

書式例:

```markdown
## Wiki

- vault: <vault 名>
- path: <vault の絶対パス>
```

以下 `<vault>` はノートのルート（宣言の `path`）。ノート指定は vault ルート相対。

| 操作 | 手段 |
|---|---|
| 読む | `read` |
| 新規 / 上書き | `write` |
| 部分置換（チェック・いま・結晶） | `edit` |
| 一覧 | `ls`（ノート一覧は `bash` `ls`） |
| 検索 | `ffgrep`（glob 指定）。シェル検索が必要なときだけ `bash` `rg` |
| 移動（`progress/` → `done/`） | `bash` `mv` |
| 削除 | 確認してから。confirm なしで消さない |

読み書きは Markdown を直接触る（`read` / `write` / `edit`）。MCP は使わない。

**検索順（タスク前）**: `ls` `global/progress` と `<module>/progress` → keywords 一覧 → `ffgrep`（必要なら path を絞る）→ `read`。

## 文書の書き出し・推敲

- 業務・技術文書（PRD、設計書、ADR、仕様書、手順書、調査・計画・報告書）を書き出す・推敲するときは **yomiyasu** を読み、それに従う
- progress / journal / keyword の**枠・語彙・フェーズ行**は **wiki** が正本。その枠の中の本文を書き出すときも yomiyasu に従う
- 通常の質問への回答には yomiyasu を適用しない
- available skills に `yomiyasu` が無いときは、その文書の書き出しだけ進めず、無いことを伝える。看板（progress）の更新そのものは止めない

## 構造と境界

```
<vault>/
├── global/           # 仕様・ドメイン・横断
│   ├── journals/
│   ├── progress/ + done/
│   └── keywords/
└── <module>/         # そのモジュールの実装知識
    └── {journals,progress,keywords}/
```

| 置き場 | 役割 | 寿命 |
|---|---|---|
| **progress** | 工事の**看板**（いま・フェーズ）。詳細なし | 短命 → `done/` |
| **journals** | 区切りの**計画 → 記録 → 結晶**。詳細の正本 | 永続 |
| **keywords** | 安定した用語・最終仕様 | 永続 |

- 区分は時間軸ではなく**内容の性質**
- **global** = 何か（仕様・ドメイン）/ サーバ×クライアント協働  
  **module** = そのモジュールでの実装。迷ったら module
- Chat/Copilot は正本にしない

| 場所 | 使う | 使わない |

## 単位（粒度）

スクラムのバックログ分割に近い。**層ごとに単位が違う**。

| 単位 | 何か | 必須の問い | サイズ感 |
|---|---|---|---|
| **progress 1枚** | 工事 = Outcome の束 | 終わると**誰が何をできる／何が解消する**か？ | おおよそ数日〜数週間で `done/` できる |
| **フェーズ 1行** | 大きな一区切り（Epic / スプリント相当）の**能力** | **「〜できるようになる」**が1つ言えるか？ | デモ or 外から検証できる一塊。journal 1本に収まる |
| **journal 計画 1項** | **着手タスク** | 何を・どこを・完了条件が、その行だけで分かるか？ | 単独で着手できる |

### フェーズ行の書き方（最重要）

文面は **能力・中間成果**。手段やチケットの袋詰めにしない。

| OK | NG |
|---|---|
| 連続シェア書き出し — 指定投稿列の export job を受け付け、完了を MB で届けられる | 後続（非ブロッカー）— export · OGP · テーマ |
| 高度 OGP — SNS がリッチカードを出せる | B3–B5 — 厚み / admin / EKS |
| like のクライアント同期 — myLikedPosts で履歴が取れ isLiked 無しで表示できる | P6 LikedHistoryRepository 実装 |

- **1行 = 能力 1つ**。無関係な能力を `·` で連結して1チェックにしない
- **能力名が空のラベルは置かない**（「厚み」「対応」「整備」だけ）。中身が固まるまで書かない。固まったら OK 形で1行追加
- 完了定義は行を読んだ外の人が検証できること。技術内訳・ファイル列挙は **journal**
- 行末に `· [[journal]]` 可。並行・依存はフェーズ直下に1行
- Obsidian タスクリスト（`- [ ]` / `- [x]`）。**表セルに `[ ]` を書かない**

### リトマス

**細かすぎ** → journal の計画へ  
（ファイル単位、「interface 作る」、単語チェック）

**荒すぎ / 袋** → 能力ごとに割る  
（完了後も「何ができたか」が1つ言えない、無関係な残件の連結、いつ `done/` するか不明）

**価値が書けない** → まだ工事にしないか、スコープを問い直す  
（手段だけ・「〜対応」だけで痛みが見えない）

数値ポイントや「理想 N フェーズ」は設けない。上下はリトマスで見る。

## progress — 看板

開いた瞬間に **いまどこ・次なに・フェーズ一覧・終わると何ができるか** が分かること。計画の骨格はフェーズ 1 本だけ。

### 書くこと

- **一言 / Outcome**: 手段だけでなく、できるようになること / 解消する痛み
- **いま**: 次に手を付ける 1〜2 フェーズ（1〜3 行。handoff が要るなら path/フラグの表 1 つまで）
- **フェーズ**: 上記「フェーズ行」のタスクリスト
- **スコープ**: 含む / 含まない（表で短く）
- **注意**: 段取りに効く落とし穴だけ（各 1 行）
- **関連**: 設計 journal・親/子 progress へのリンク

### 書かないこと

設計図・型・コードマップ・mermaid・cd 手順・ビルドログ・フェーズ内の詳細チェック・「やること」の二重リスト・セッション済みログ・能力名のない袋フェーズ

### 命名・配置

- 工事名は**動詞化**（〜導入 / 構築 / 移行 / 対応 / 確定 / 廃止）。keyword と衝突させない
- 横断: `global/progress/{工事名}.md` が**唯一の横断一覧**（子の能力は要約＋リンク。子の詳細を複製しない）
- 子: その module 固有の能力フェーズだけ。薄い
- module のみ工事: `<module>/progress/{工事名}.md`

### 整形の参考

1 行 1 能力のフェーズ行だけで骨格を作る（詳細は journal へ）。骨格の参考でありコピー元ではない。

## journals — 詳細の正本

1 区切り（フェーズ or 設計まとまり）の作業文書。progress は薄いので、**曖昧な journal = 工事が復元不能**。

### 自己完結（最優先）

この journal だけ開いた人が、会話なしで **何を・どこを・どうなれば完了か** 分かる。

計画 1 項に含める:

| 必須 | 任意 |
|---|---|
| **何を**（現象 or 意図。jargon だけ禁止） | 制約・リスク |
| **どこを**（主要パス・シンボル） | やらないこと |
| **どうなれば完了**（外から検証） | |

種類: **方針・設計**（結論・比較の残す部分・契約） / **区切り**（目的・計画・記録・結晶）

### 書かないこと

単語・番号だけのチェック、progress フェーズ一覧の複製、調査生ログ丸ごと、コード大量貼付、「前回チャット参照」だけ

### 結晶化（区切り完了時）

記録を削るか結晶へ吸収。残すのは目的・結晶・（必要なら）計画の最終形。  
未解決は **完了定義を journal に残したまま**、progress のいま/フェーズへ 1 行ポインタ。  
目安 200 行超は過程過多。完了定義の不足を行数で補わない。

命名: `<module|global>/journals/yyyymmdd.連番.知識名.md`

### ライフサイクルと status（結末まで閉じる）

journal は **開く → 途中 → 結晶 → 閉じる** を frontmatter の `status` 1 行で辿る。
「merge待ち」や途中報告のまま放置しない。**閉じるまでが journal の完了**。

| status | 意味 | 誰がいつ付ける |
|---|---|---|
| `進行中` | 開いた。目的・完了定義あり | 作成者（開くとき） |
| `merge待ち` | 結晶済・コード差分あり。main merge は司令塔 | レーン（結晶時） |
| `merged` | main merge 済 | 司令塔（merge/撤収の**同一ターン**） |
| `検証完了` | 結晶済・コード差分なし（merge 不要） | レーン or 司令塔（検証記録時） |
| `中止` | やめた。理由を結晶に 1 行 | 判断した側（区切り時） |
| `延期` | 後でやる。理由と再開条件を結晶に 1 行 | 判断した側（区切り時） |

- **結晶 = 3 点**: 問題は何だったか / 何をしたか / 結果どうなったか。長文ログは書かない。経緯・実装・検証・git を混ぜない
- **形式は固定しない**。その点がいちばん早く分かるかで選ぶ（箇条書き、短い文、表、mermaid）。図のための図・形式のための形式は置かない。mermaid の向きは下記「図」
- **変更ファイル**（コード差分があるとき必須。「何をしたか」の直後）: 下記「変更ファイル」（スキャン用の表。ここだけ形を固定）
- commit / branch は結果の末尾 1 行まで
- 新規 journal の frontmatter に `obsidianUIMode: preview`（プレビュー固定。表と details を読む）
- **閉じる義務**: レーンは最大「結晶 + `merge待ち`（or 検証記録）」まで。司令塔は merge/撤収の**同一ターン**で `merged` に閉じる。計画だけの journal も区切り時に `検証完了` / `中止` / `延期` のいずれかに閉じる（コード差分があれば `merge待ち` → 司令塔が `merged`）
- **status の置き場**: frontmatter の `status:` を正とする。本文冒頭に進捗を書く慣例がある場合も、閉じるときは frontmatter と矛盾させない（既存ノートは冒頭行だけでも可。新規は frontmatter）
- 冒頭の status と結晶の記述が矛盾したら、**結晶を正として status を直す**
- テンプレ: 本 skill の `journal.md`（vault の `Templates/` に正本を置かない）

#### 変更ファイル

表の直上に `基準:` を 1 行（レイヤーディレクトリの親。例: `src/` や `packages/api/src/`）。
path は基準からの相対（`domain/foo.ts`）。フルパスを各行に書かない。
基準を跨ぐ行（`test/` や `scripts/`）だけ、その起点から書く。

| | 概要（常時） | 詳細（開く） |
|---|---|---|
| 粒度 | その層がこの変更で担った役割。1 文 | このファイルでやった作業の列挙 |
| 書かない | 関数名の羅列、path の繰り返し | git diff の復唱、import、整形、「何をしたか」全体のコピー |

- 概要は詳細の 1 行目コピーにしない（役割 vs 作業）
- 詳細が空なら `<details>` を置かない。概要だけをセルに書く
- 詳細は HTML の `<ul><li>`（表セル内は Markdown が描画されない）
- tree にしない。ファイル見出しでページ分けしない

形:

````markdown
基準: `packages/api/src/`

| path | 概要 |
| --- | --- |
| `domain/foo.ts` | <details><summary>役割 1 文</summary><ul><li>作業</li></ul></details> |
| `domain/demo/bar.ts` | 引数追加のみ。I/O しない |
````

### 依頼 journal（対岸依頼）

対岸（他リポジトリ）の能力・ブロッカー解消を**別監督へ渡す**ときの依頼文書。
正本はこれ。対岸から依頼元への `mux_intervene` はしない（wiki が郵便、`kind=peer` が呼び鈴）。
枠（frontmatter と見出し）は `peer_supervisor open_journal` が固定してよい。中身と対岸 progress 1 行は人が書く。

**依頼 journal に使ってよい終端**（レーン journal と混ぜない）:

| status | 意味（依頼元から見た完了） |
|---|---|
| `検証完了` | 対岸の能力が main に載った（またはコード不要）。受信検証してよい |
| `FAIL-<module>` | この対岸でも無理 |
| `中止` / `延期` | やらない。理由を結晶に 1 行 |

**使わない**: `merge待ち` / `merged`。それは対岸の **レーン journal**。対岸監督は先に自分のレーンを merge し、そのあと依頼 journal を `検証完了` にする。

- **依頼元が書く（開くとき）**: `status: 進行中` + 見出し `依頼 <marker>`（`lane_watch` / `peer_supervisor` の `label` と一致）+ 何を / どこを / どうなれば完了 + 対岸 progress パス
- **対岸監督が返す**: 自レーンを merge/撤収したあと、依頼 journal を結晶（3 点。コード差分があれば変更ファイル）して上表の終端にする。依頼元タブは触らない。自分のタブは残す
- **閉じるまでが完了**: `進行中` のまま放置しない。`kind=peer` は frontmatter `status:` を先に読む
- **依頼元が PEER_EVENT でやること**（`next=` を見る。対岸タブは閉じない。peer watch は extension が外す）:
  - `next=resume_verify`（`検証完了` / `PASS` / 差分なし系）: 元の FAIL レーンは merge しない。受信検証を空き枠の**新レーン**にする。自 progress「いま」を更新。ユーザー応答末尾に結晶の要点
  - `next=deny_no_workaround`（`FAIL-*`）: 自側 workaround 禁止。次の module なら新しい依頼。でなければユーザーへ
  - `next=stop`（`中止` / `延期`）: 受信検証しない。progress にポインタ
  - `next=inspect_journal`: 終端語彙を確認して上のどれかに落とす
- 共有 journal でもよい。見出しに依頼 marker を入れ、`label` と一致させる

### 何をやったかの解説（journal 書いたら必須）

結晶を journal に書く（チャットだけに置くな）。書き方は上記「結晶」と「変更ファイル」。
ユーザーに見える応答があるなら、そのターンの**最後**に要点を伝える。レーン子の TUI はユーザーに届かないので、正本は journal。司令塔は完了・merge の応答で、journal から何をやったかの要点を伝える（全文転記・ログ・手順の復唱はしない。transcript 深読みはしない）。

## keywords — 安定定義

- **一言定義**（コードなしで分かる 1〜2 文）
- **関連** `[[journals]]` / `[[progress]]`
- 必要なら: 仕組み、連携、落とし穴、ドメイン固有の意味・制限
- 書かない: コード本体、git 履歴、網羅 API

パス: `<module|global>/keywords/名前.md`  
フロントマターに tags / aliases を適宜。

## 読み方・ワークフロー

**読む順**

1. progress → いま・フェーズ・Outcome
2. 該当 journal → 計画を進める / 記録を短く
3. 区切り完了 → 結晶化、progress の `- [x]` といまを更新
4. 工事完了 → 安定部分を keyword、progress を `done/`（読み取り専用）

**起こす**

1. 工事名（動詞化）と Outcome を決める
2. 配置（global umbrella + 子 / module のみ）
3. progress を看板として作成（フェーズは能力行）
4. 設計が要れば方針 journal、フェーズ着手で区切り journal（相互リンク）

**日常**

progress のいま → journal の計画 → 発見は記録に短く → 区切りで結晶と progress 更新

**検索（タスク前）**

上の「検索順（タスク前）」に従う。

**肥大化**

- progress に設計・パス・型が増えた → journal へ
- 「いま」が長い → handoff 以外を削る
- 子と umbrella の文重複 → 片方へ
- journal の長い記録が完了後も残る → 結晶化
- フェーズが袋になった → 能力行に割る

## 図

結晶の 3 点の**中**に置いてよい。progress 看板に大きな図を置かない。その点の理解に効かない図は置かない。

| 図 | 向き |
|---|---|
| flowchart | 所有 / 配線 |
| sequence | 書込順 |
| stateDiagram | 状態機械 |
| Canvas | 画面横断の大関係 |

- レビューアは結晶 → 変更ファイル → 差分の順で読む（図は 3 点の中）
- Obsidian 固有構文は **obsidian-syntax** スキルに従う

## アンチパターン（再発防止）

| NG | 正しい場所 / 直し方 |
|---|---|
| progress が設計書・コードマップ化 | journal 結晶 |
| フェーズと「やること」の二重管理 | フェーズ 1 本 |
| 表セルの `[ ]` | `- [ ]` リスト |
| フェーズがファイル作業単位 | journal 計画へ落とす |
| **無関係な残件の袋フェーズ**（`export · OGP · B3–B5`） | 能力ごとに1行。空ラベルは書かない |
| Outcome なしの「〜対応」工事 | 一言に価値を書く or 分割し直す |
| journal の `C3 あとで` / 単語チェック | 何を・どこを・完了条件 |
| 子 progress に umbrella 長文コピー | umbrella が一覧、子は薄い |
| `done/` を通常の編集対象にする | 読み取り専用アーカイブ |
| 結晶が読みにくい長文 / 形式の固定（箇条書きだけ 等） | その点がいちばん早く分かる形（箇条書き・短い文・表・mermaid） |
| 変更ファイルにフルパス連打 / tree | 基準 1 行 + レイヤー起点の表 |
| 変更ファイルが path だけ / 概要なし | 概要 1 文。詳細は作業の列挙 |
| 詳細が diff 復唱 | 判断が残る変更だけ |
| 表・見出しだけの骨組み | 3 点の中身を書け |
